LU factorization

Wrap the input to select AlgorithmicNLA through LinearAlgebra, or use the qualified package function on ordinary backend arrays:

julia> using AlgorithmicNLA, LinearAlgebra

julia> A = [0.0 2.0; 1.0 3.0]; F = lu(NLAArray(A));

julia> Array(F.L) * Array(F.U) == A[F.p, :]
true

julia> F \ [1.0, 2.0]
2-element Vector{Float64}:
 0.5
 0.5

julia> AlgorithmicNLA.lu(A).p == F.p
true

lu! overwrites its input. Both entry points return LinearAlgebra.LU with NLAArray factors and backend pivot storage. Floating-point input retains its element type. Allocating LU of integer input follows Julia's lutype conversion; callers choose conversions explicitly for floating-point input.

The interface supports rectangular factorization, RowMaximum, NoPivot, RowNonZero, check, and allowsingular. The allowsingular behavior is also provided on Julia 1.10. check=true rejects nonfinite input before mutation; check=false leaves responsibility for checking F.info or issuccess(F) to the caller. A negative info denotes a failed NoPivot factorization, and a positive info records the first exact zero pivot. Zero pivots in NoPivot still throw when check=true, allowsingular=true.

F.L, F.U, and F.P allocate on the factor backend. F.p explicitly copies pivots to the host and constructs Julia's permutation vector. Square factors support vector/matrix solves, ldiv!, transpose and adjoint solves, right division, inv, det, and logabsdet. Right-hand sides should reside on the same backend as the factors. Allocating solves preserve the right-hand side's backend and use Julia's result element-type rule without converting the factors.

Algorithm and device execution

The driver follows LAPACK 3.12.1 GETRF, including recursive GETRF2 panels, pivot application to both sides of each panel, triangular substitution, and mul! trailing updates. The default block size is 64, as in reference ILAENV; blocksize can be changed for measurements and boundary testing.

Pivot selection uses a dimension-wise mapped reduction over metric/index pairs, retaining the result on the device and writing its index directly into pivot storage. The metric vector and separate value/index outputs are not materialized. Device reductions use suffix lengths rounded up to powers of two (capped by the row count), with completed rows contributing neutral metric/index pairs. This limits reduction-length specializations to logarithmically many per matrix; ordinary CPU arrays scan only the active suffix. The extra device scan is less than twice the active length and does not change the eligible pivots. LAPACK's complex pivot metric is abs(real(z)) + abs(imag(z)); this intentionally differs from Julia's generic non-BLAS complex path, which uses abs(z). Ties choose the first row. There is no host read of each pivot.

Pivot application follows LASWP: one map! worker per column applies its swaps sequentially in the requested order. Different columns are independent, so overlapping pivots and reverse application need no inter-worker synchronization or row workspace. Pivot indices are read inside the device map. Transpose/adjoint map destinations are normalized to their underlying storage, preserving conjugation and device dispatch.

Triangular substitution recursively partitions triangles larger than order 16 and updates with mul!. Small blocks use reference BLAS TRSM forward/back substitution inside map!, with one independent worker per right-hand-side column. The scalar accesses run inside the device map; each worker modifies only its own column. Unit diagonals and the unused triangle are not read. Arithmetic is rounded to right-hand-side storage at each update, with the existing robust complex division. It does not use Metal's native MPS triangular solver, whose Float16 dispatch currently aborts. Existing backend operations supply all device kernels; this package has no direct KernelAbstractions dependency.

Column scaling uses map!, reading the one-element diagonal view inside the map. GPUArrays supplies its kernel with runtime dimensions, avoiding Metal's repeated broadcast specialization as the column shrinks. The diagonal and destination views are disjoint; no host pivot or diagonal read is required.

The reciprocal-versus-division branch uses LAPACK's safe minimum. Complex scalar division follows LADIV scaling, with Float32 arithmetic for Float16/BFloat16 components and the original precision for wider components. Results are rounded back to the stored element type. Julia's inv(::ComplexF32) returns ComplexF32 but explicitly widens its intermediates to Float64, which Metal cannot execute. Metal supplies a Float32 device override for complex division; the common LADIV implementation here also covers generic low-precision types and LAPACK's overflow/underflow scaling. GEMM accumulation remains the backend's choice; factor storage is never implicitly widened.

LU inherits the backend's floating-point arithmetic, including flushing subnormals to zero. On Apple GPUs this affects Float32 and arithmetic using Float32 intermediates, including BFloat16. A stored subnormal pivot can therefore compare equal to zero or produce an invalid multiplier. Such inputs do not have CPU LAPACK's gradual-underflow guarantees. This follows the Metal arithmetic specification (section 8.1); no software emulation or whole-array promotion is performed.

Input finiteness validation and the final status transfer synchronize. check=false suppresses validation/errors, but constructing a standard LU still needs its host info field. Benchmark timings include that transfer.

Numerical validation

The LU tests use LAPACK 3.12.1 GET01 and GET02 ratios, with the threshold strictly below 30 from all four precision-specific test input files, including dtest.in. No universal baseline multiplier is used.

  • Reconstruction: norm(L*U - A[p,:], 1) / (n * norm(A, 1) * u).
  • Solve: the maximum over right-hand sides of norm(b - op(A)*x, 1) / (norm(op(A), 1) * norm(x, 1) * u).

Here matrix norms are induced 1-norms and u = eps(realtype(T))/2, matching LAMCH('E'). Complex solve vector norms use sums of abs(real)+abs(imag), as in ZGET02's DZASUM; its matrix norm uses complex absolute values.

The corpus adapts the eleven general-matrix families from CHKGE/LATB4: diagonal, upper/lower triangular, conditioned dense, three zero-column patterns, two ill-conditioned cases, and small/large scales. Generic high-precision QR constructs their spectra; it does not reproduce LATMS's exact random matrices. Generation uses LAMCH('P') = eps(T) for the prescribed condition numbers and scales, distinct from the residual normalization. Additional tests cover rectangles, block boundaries, pivot ties, safe-minimum division, and API behavior. The tiny-pivot regression probes subnormal arithmetic separately: gradual-underflow backends must pass, while flushing backends record the unavailable IEEE behavior as an expected broken test. The GE-family gates retain the same threshold.

Residuals are evaluated in widened CPU arithmetic from the represented input and stored factors, using the input precision's u. This prevents residual evaluation overflow in low precision. It is an explicit adaptation of LAPACK's evaluation arithmetic, with the same ratios and threshold. Supported CPU types also run LAPACK reference factorizations through the same reconstruction gate.

The shared corpus runs on CPU and Metal; CUDA hardware validation remains outstanding. Performance measurements are informational until the release crossover target is demonstrated on hardware.

The GEMM results demonstrate useful backend throughput, while the LU compilation growth and blocking overhead need investigation before extending the size sweep.

The mapped reduction alone reduced the best 512-by-512 LU time from 488 to 452 ms (about 7.5%). The final map! scaling path adds some execution overhead, but avoids the expensive broadcast specializations encountered during repeated calls. Ordered pivot application

A subsequent pass replaced the three-copy implementation of each row swap with mapped, ordered swaps. This retains the small-triangle optimization above and removes the row workspace from LU, solves, and permutation-matrix construction. Pivot selection, factor storage types, and numerical acceptance thresholds are unchanged. An isolated probe applying 1024 pivots to eight columns dropped from about 11.3 ms to 0.33 ms; the pivots repeatedly targeted the final row, exercising overlapping swaps.

Remaining performance options

The reported roughly fivefold gap to LAPACK at size 8192 motivates a new phase profile after the swap changes. That user-reported result has not been reproduced in the checked-in measurements; its timing configuration remains to be recorded. The following are hypotheses, not measured speedups:

  1. Retune blocking and inspect delegated GEMM. Compare complete LU with block widths 64, 128, 256, and 512, alongside its actual trailing-update views and alpha=-1, beta=1 products. Panel optimizations can change the best width. Compare supported backend GEMM implementations with the same update contract; an accelerated path for plain A*B need not support LU's accumulating update.
  2. Reduce panel launches and temporary reductions. Each current column leaf separately selects a pivot, writes its index, swaps its diagonal entry, updates status, and scales below the pivot. Preallocated reduction scratch and fusing compatible steps are candidates. The recursive panel also invokes many tiny solves and products. A cooperative small-panel/base-case kernel could retain the reference dependencies with fewer launches. It needs deterministic pivot ties, safe-minimum handling, and a valid reduction across all candidate rows.
  3. Investigate scheduling only where the profile justifies it. Submission batching can reduce host overhead, but it does not fuse device work. Overlapping preparation of the next panel with a disjoint trailing update (look-ahead) is a larger option requiring explicit dependencies, stream support, and an audit of pivot effects. It is not the first implementation change to make.

These can be implemented in Julia. KernelAbstractions is the portable candidate when cooperative execution exceeds what the existing array primitives express. The inspected rocSOLVER GETF2 source contains fused pivot/status/swaps and optional specialized small/skinny-matrix kernels. This supports investigating fusion; its dispatch conditions and numerical details are not a substitute for our LAPACK contract or measurements on Metal.

Start with an uninstrumented warmed baseline and a phase profile at representative small and large sizes, then the bounded block/GEMM comparison. Use the performance workflow to estimate how much of the total gap the measured dominant phase can explain before committing to a panel-kernel rewrite.

Views select a different GEMM implementation

Installed-source inspection and method lookup identify a material difference: Metal's mul! for range views (src/linalg.jl:114) selects its native GEMM path under :auto; contiguous MtlMatrix operands (src/linalg.jl:70) can select MPSGraph. A standalone dense matrix multiplication therefore does not measure the implementation used by our LU trailing updates.

A separate probe measures the actual first update at size 4096 with alpha=-1, beta=1, preserving its parent leading dimension and offsets. Decision

Competitive LU at 4096 is a credible target, while 2048 is more demanding. The current evidence favors a substantial change in execution strategy over further small block-size adjustments alone:

  • Prototype a cooperative panel/base-case implementation preserving the LAPACK dependencies, pivot ties, safe-minimum handling, and numerical gates. The existing independent maps do not address all panel launches and reductions.
  • Improve GEMM execution for the actual views, through backend support or measured packing/workspace strategies. At 4096/256, deleting even the entire measured panel phase would leave about 160 ms in the instrumented run, so a panel-only optimization is not a sufficient demonstrated route to the 129 ms CPU target.
  • Test a complete 4096 factorization after these bounded prototypes before committing to a wider kernel rewrite. For planning only, panel <=50 ms and trailing updates <=30 ms, with other costs near 45 ms, would fit the current CPU timing budget. These are unachieved performance targets, not numerical gates.

Explicit GPU kernels can remain in Julia: Metal.jl compiles Julia kernels to Metal functions, and KernelAbstractions provides portable workgroup programming. See Metal's compiler API and the KernelAbstractions quickstart. The measurements establish neither a need to switch source language to Metal Shading Language nor a guarantee that portable kernels will match MPS.

Reproduce with benchmarks/lu_feasibility.jl and benchmarks/lu_update_feasibility.jl in the test/metal environment. Their raw samples live in benchmarks/results/lu-feasibility.csv and benchmarks/results/lu-update-feasibility.csv; see benchmarks/README.md for arguments and timing boundaries. CUDA and other precisions were not measured.

Cooperative panels and MPS views at 4096

The bounded prototype requested after the feasibility study reached roughly CPU LAPACK timing on 4096-by-4096 Float32 matrices. It lives in benchmarks/lu_cooperative.jl as CooperativeLU.factor; the public package LU implementation remains unchanged. This is evidence to continue development, not a release-level performance claim or a complete replacement of the public API.

The cooperative kernel executes a small GETRF2 dependency schedule inside one 256-thread workgroup. That group scans every candidate pivot row, reduces with first-index tie breaking, and performs the required swaps, scaling, triangular substitution, and updates in dependency order. It uses workgroup-local reduction storage and barriers covering global and local memory. Larger panels retain the recursive driver and backend matrix products. This avoids a device-wide barrier or an assumption that multiple workgroups can synchronize inside the kernel. GEMM accumulators use at least Float32, following the backend convention, with results rounded into the original factor storage. Safe-minimum scaling reuses the existing implementation.

The MPS adapter constructs matrix descriptors with each view's byte offset and leading dimension, encoding the product with reversed operands for column-major storage. Inputs and outputs remain views of the original buffer; no packing or copy-back is required. This adapter is specific to Metal and currently restricted to Float32, while the panel arithmetic is written with KernelAbstractions. Its MPS encoding adaptation is credited in licenses/Metal.txt.

Scope and next decision

The feasibility experiment succeeded at the agreed 4096 target, so its result does not trigger the proposed performance pause. The next implementation work is integration: preserve the complete LU interface and fallback coverage, place the Metal-specific descriptor adapter behind backend dispatch, and validate kernel execution on other backends. Production integration must also cover supported pivot strategies and rectangular/wrapped inputs. The prototype currently accepts square MtlMatrix inputs with partial pivoting and returns singular status without implementing the full public exception policy.

The standard AlgorithmicNLA.lu has not acquired this acceleration or a new dependency. KernelAbstractions is an explicit dependency of the Metal experiment environment. Run benchmarks/lu_cooperative_bench.jl, benchmarks/lu_cooperative_confirm.jl, and benchmarks/test_lu_cooperative.jl with --project=test/metal; instructions are in benchmarks/README.md. Raw samples and final-case residual ratios are preserved in benchmarks/results/lu-cooperative.csv and benchmarks/results/lu-cooperative-confirm.csv.
